# Atlas Agent 问数：格式、等待、多表歧义与展示诊断

> 历史诊断记录：后续用户已明确unit本身就是转换规则（%乘100、万元除10000等），无需额外精度/尺度字段。下文有关额外维护百分比尺度的建议已撤销，当前实现及部署以 [单位驱动展示说明](agent-query-quality-implementation.md) 为准。

## 范围与结论

本次针对用户提供的结果表和调用耗时截图，检查 Atlas 的 MCP、内部问数、查询执行、Package、检索、插件规则，并只读参考 Eureka 认证连接实现。没有修改查询口径、执行 MaxCompute 查询、读取客户端私有凭证或调用澄清卡片。

另对当前项目配置的 PostgreSQL 做了只读元数据/任务时间核验；它不是部署环境的完整链路实测，不能与截图每次调用逐一关联。没有重放用户 SQL，也没有产生新仓库查询。

核心结论：不是四条提示词没写好，而是展示格式契约缺失、异步工具交互方式、多表来源确认不足，以及网页/插件呈现规则未彻底分离叠加。

## 1. 百分比与两位小数

### 已确认的证据

- `query-compiler.service.ts` 的输出列只传 `id/name/type/unit`；`QueryResultColumn` 和外部响应 Schema 也没有展示精度或百分比尺度。
- `query-execution.service.ts::parseResult` 保留原始结果字符串，不按单位转换或舍入；这有利于精度保真，不应该直接改成把原始值 ROUND 后覆盖。
- `ExternalDataService.result` 将保存结果原样返回，MCP 没有确定性的显示值/表格生成步骤。
- 内部网页 `query-result.tsx` 也直接 `String(value)`，仅在“口径与来源”中显示单位，因此不是只有 MCP 会受影响。
- 当前本机已发布语义中：

| 指标 | 单位 | 正式公式 |
| --- | --- | --- |
| 加购率 | % | `SUM(fl_cart_num) / NULLIF(SUM(fl_uv), 0)` |
| 支付转化率 | % | `SUM(fl_pay_byr_num) / NULLIF(SUM(fl_uv), 0)` |
| 下单转化率 | % | `SUM(fl_crt_byr_num) / NULLIF(SUM(fl_uv), 0)` |

这些派生公式产出比值，单位已保存，不是再次发布一次 `%` 就能修复。近期保存的任务输出列中也能找到 `%` 元数据，但展示层未执行格式化。

### 合理修复

1. 原始 `rows`、null、大整数/高精度字符串不变；增加统一的展示格式契约和共享格式化函数，让内部网页与 MCP/插件使用同一规则。
2. Decimal 与百分比默认显示2位小数，已明确配置精度或用户明确要求时遵循配置；整数计数保持整数，ID/日期/字符串不能误格式化。
3. `%` 必须区分底层为比值（乘100展示）还是已是百分数（不再乘100）。例如比值 `0.04457756` 显示 `4.46%`，已是百分数的 `4.457756` 也显示 `4.46%`。不能只凭列名有“率”或值小于1猜尺度，尤其不能把已经乘100的公式再次乘100。
4. 先核验现有百分比字段/公式的尺度，再写入正式语义展示元数据并随 Package 版本发布。元数据缺失且不能证明尺度时不得擅自转换。
5. 可提供限定展示行数的 `display_rows` 或服务器生成的 Markdown 表格，让宿主直接采用确定性显示值；不要把5000行原始结果再整份复制成显示字符串，增加体积和模型耗时。原始结果继续用于校验与下载。
6. 表头明确单位（如 `加购率（%）`、`平均停留时长（秒）`），null 显示空值标记，不改成0。

附带口径风险：本机还有名为“支付转化率”“下单转化率”、聚合为 `AVG` 的原子指标，与上述派生指标共存。平均原子率和汇总人数之比不是天然同一口径。需先按治理说明区分并确认，不应由格式化代码替换公式，也不能断定截图实际用了哪一种。

## 2. sleep 与 MCP 端到端偏慢

### 已确认的链路差异

- 插件 `plugin-skill.ts` 及 `mcp-data.service.ts` 明确建议至少间隔3秒轮询。外部 `query_data/get_dimension_values` 只返回任务，通常需提交→等待→状态→结果，多次模型/工具往返；宿主选用终端 `sleep` 是执行策略，不是仓库 SQL 语句。
- 内部 `ask-run.service.ts` 的两种数据工具都在一次工具调用中 `waitForQuery`，服务端1秒检查一次，完成后直接返回结果摘要。模型不必自己执行 shell 等待或调度状态/结果两个调用。
- 查询执行后台每3秒检查活动任务，读状态时也可主动刷新。内外共用 `QueryExecutionService` 和同一编译器/MaxCompute 提交路径，不能笼统说 MCP 使用了更慢的查询引擎。
- Eureka 的 adapter `requestHeadersCommand` 每个 HTTP 请求会启动可信请求头进程；当前 Haze hook 会读取/校验会话并获取本人个人凭证，Atlas 随后再实时校验个人凭证。OAuth access token 已有未到期复用，不能说每个请求都会刷新 OAuth，但每个 HTTP 请求的进程/凭证获取仍有额外开销。
- `get_query_session` 的 `describe` 调用 `selectable.list()`；后者为所有可选表重建 Package，即使只是读范围版本也会加载完整字段/目录关系。
- MCP 搜索路径：会话范围解析重建一次全部 Package，`SemanticScopeService.resolve` 又列表重建一次，再逐表 get 构建一次；查询/Package 入口也有重复元数据工作。内部问数存在相似的元数据重建问题，不能把它视作只影响 MCP 的缺陷。

### 本机只读采样（不代表截图/生产基准）

| 项目 | 本次观测 |
| --- | --- |
| 当前可选表数 | 2 |
| 可选表列表冷读 | 约2309ms，构建2个 Package，含连接/冷态影响 |
| 可选表列表再次读取 | 约16ms，仍构建2个 Package |
| ALL 范围 resolve | 约197ms，构建4个 Package |
| 本地元数据“流量”检索 | 约51ms，返回2个候选表 |
| 近期10个 MCP 任务的保存完成耗时 | 约2.6–7.3秒，包含提交和完成检测，不是纯引擎 CPU 时间 |

截图显示 `sleep 3` 的工具阶段耗时22秒，不等于 sleep 本身执行22秒；可能包含 shell/WSL 启动、工具调度、权限或事件计时开销。当前没有截图对应的请求ID及分段计时，不能确定这22秒的准确来源。同理，`get_query_session` 15秒不能仅凭两表热读16ms就归因数据库。

### 合理修复

**优先减少交互轮次，而不是删掉限流或让模型无间隔轮询：**

1. 数据提交提供有界等待，短任务完成时直接带结果返回；未完成继续返回同一任务ID。结果工具支持有界长轮询，合并“查状态→读结果”，替代模型运行 shell sleep。等待时限需符合宿主/代理的请求超时，不能无限挂起；不得重复提交任务，取消、超时、结果过期及幂等边界保持不变。
2. `get_query_session` 返回轻量范围摘要，按需再取目录；范围有效性仍检查，不把 invalid SELECTED 回退 ALL。可选表列表改为轻量元数据读取，不为显示表名重建完整 Package。
3. Package/检索复用按正式语义发布修订失效的缓存或索引，撤下/编辑/发布及时失效。不简单改读可能过期的 `semantic_package.content`，也不缓存身份授权来换速度。
4. 评估 Eureka 请求头子进程与凭证获取开销，尽量复用受保护的连接/可信层能力；继续保证用户隔离与凭证重置/停用生效，不能把凭证放入模型/URL/Skill，不能跳过 Atlas 实时身份校验。
5. 增加不含凭证的分段计时：宿主调度、请求头进程、个人凭证获取、Atlas Haze 校验、范围/Package、提交、仓库完成检测、结果读取、模型整理。用同一表/SQL/日期/限制做授权 A/B 对比，分别看冷态/热态中位数和P95，再决定是否需要优化仓库 SQL。

## 3. 全选后没问采用哪张流量表

### 已确认的原因

- ALL 只表示允许搜索/查询这些表，不表示用户确认将所有表合并，也不表示首条命中就是业务来源。
- `semantic-asset-search.ts` 将候选排序并返回，`AMBIGUOUS` 主要表示一张表内某个名称命中多个精确资产；没有跨表来源歧义的总标记或查询前确认门禁。
- 只用 `keywords:['流量']` 时，本机两个业务粒度差异明显的表都会成为候选，coverage 为 `UNSPECIFIED`，不代表已经确定口径。排序末尾还可能按 table_id 决胜，不是业务判断。
- 当前插件仅泛称“有歧义先问”，Eureka 专属规则列举时间、指标、店铺、维度，没有明确强调来源表、业务主题和粒度选择。主规则也没有规定不能把候选排序当作来源确认。
- 仅安装声明澄清能力不等于本轮已开放宿主工具，还需核对入口/所属 Skill 激活与实际工具权限。此代码诊断任务明确关闭了 request_user_input，不代表此前业务截图中的运行状态；不能据此推断此前没有工具。

### 合理修复

1. 跨表返回结构化歧义说明：候选业务名、来源、用途/描述、粒度、请求指标覆盖与关键口径差异。候选多不应一律提问；已有明确来源、单一合理候选时直接继续。
2. 用户只说“流量”且多个表在用途/粒度/口径上都合理时，先确认“商品来源明细、店铺汇总、其他渠道”等真实候选，不编造表或默认选第一张。可以先推荐并解释差异，但必须等待确认。
3. 同表内原子AVG率与派生汇总比值也属于需要识别的指标口径歧义。
4. Eureka 有宿主 request_user_input 时调用卡片；成功后停止当前轮等待继续；未提供工具时用普通文字问，不直接猜。保持原 session_id、选数和 scope_revision，选表仍使用目录页面。
5. 若产品要求严格禁止未确认来源就产生查询费用，需要额外的服务端查询上下文/确认门禁：把当前问题对应的候选歧义及确认来源绑定范围版本，提交时验证。只加提示词或 `needs_clarification` 布尔值仍由模型遵守，不能宣传是强制保证；门禁也不能把旧问题的歧义无条件套到后续所有查询。

## 4. 结果默认表格、文字只用于结论与汇总说明

### 已确认的规则冲突

网页默认 prompt 明确写有“已选择最终查询结果时，页面默认展示实际结果表……回答中不要重复生成数据表格或逐行抄写结果”，因为网页有 `present_query_results` 和原生结果卡片。

插件将有效网页 prompt 原样打入 `references/current-rules.md`，但插件没有该网页结果卡片。宿主适配只说“文字和表格”，没有清楚覆盖网页的“不要重复生成数据表格”规则，因此存在呈现语义冲突。Eureka 的普通 Markdown 表格也不会自动执行 Atlas unit 及精度转换。

### 合理修复

- 将共享业务口径规则与网页专用呈现规则真正分层。插件必须明确：没有自动结果卡片时，实际成功结果默认生成 Markdown 表格；不要把网页“避免重复表格”照搬到插件。
- 数据明细和分组结果以表格为主；说明性文字只用于必要结论、汇总解释、来源/日期/单位及截断限制，不逐行把表格改写为长段落。汇总数字本身仍可用小表展示。
- 使用第1节统一显示值，不让模型随意补百分号或计算舍入；保留原值以便核对。
- 只用最终成功查询结果，不混入候选值/探索过程，不把截断明细自行求和为全量结论。较长结果按展示上限分页/摘要并明确限制，不假装全部展示。

## 推荐实施顺序及验收

| 优先级 | 交付 | 核心验收 |
| --- | --- | --- |
| P0 | 统一格式契约与格式化，插件表格规则隔离 | 比值%/已是百分数/空值/高精度/大整数均正确；两位小数；网页与插件一致 |
| P0 | 来源/口径歧义识别与澄清，必要时增加提交门禁 | 多个合理流量源先澄清；明确来源不多问；跳过不查；原会话/选数保留 |
| P1 | 有界等待与结果合并，去掉 shell sleep 执行策略 | 常见短任务减少模型/工具往返；长任务可取消/超时/恢复，幂等不变 |
| P1 | 轻量范围查询、Package 重复构建优化 | 大范围元数据开销下降，语义更新与撤下即时生效，隔离与鉴权不退化 |
| P1 | 全链路无秘密计时与授权 A/B 验证 | 明确耗时在调度/鉴权/元数据/执行哪一段，不用截图总时长猜引擎速度 |

本次完成定位与方案，未将上述修复直接部署或改变既有查询口径。真实查询、跨端格式展示、宿主卡片和速度收益仍需在修复后进行授权联调；不能以元数据采样或提示词测试代替。
